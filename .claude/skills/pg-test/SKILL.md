# pg-test

`/pg-create`가 만들어둔 `SolutionTest`에 **공식 입출력 예 외의 추가 케이스**를 붙인다.
"테스트 케이스 1번은 통과하는데 제출하면 일부 실패/시간초과" 같은 상황에서 원인을 좁히는 게 목적이다.

## 입력

`/pg-test [폴더 경로] [증상]`

- `[폴더 경로]`: 생략하면 `java/src/pg`와 `kotlin/src/pg`를 통틀어 가장 최근에 수정된 `Solution.*`이 속한 폴더.
- `[증상]`: 선택. 예) "일부 케이스 실패", "시간 초과", "효율성 테스트만 실패". 주면 그 증상에 맞는 케이스를 우선 만든다.

## 절차

1. **현황 파악**: 대상 폴더의 `README.md`(문제 링크), `Solution.*`(현재 풀이), `SolutionTest.*`(이미 있는 케이스)를 읽는다.
   - `SolutionTest`가 없으면 만들어도 되지만, 그 전에 `/pg-create`로 만든 폴더가 맞는지 확인한다.

2. **문제 제약조건 확인**: README의 링크를 WebFetch로 읽어 제한사항을 다시 가져온다 (입력 크기 상한, 값 범위, 중복 허용 여부, 동률 처리 규칙 등). 경계값 설계의 근거가 되므로 추측하지 말고 실제로 읽는다.

3. **현재 풀이의 약점 분석**: `Solution` 코드를 읽고 아래를 짚는다.
   - 시간복잡도가 제약조건 상한에서 통과 가능한지 (예: n ≤ 500인데 O(n³)이면 위험)
   - 입력 배열을 파괴적으로 수정하는지, 정렬 안정성에 의존하는지
   - 동률(tie)일 때 우선순위 처리, 빈 입력/단일 원소, 0이나 최댓값 같은 경계
   - 증상이 주어졌다면 그 증상과 연결되는 지점을 우선 본다

4. **케이스 추가**: 기존 `SolutionTest`의 스타일(번호 매기기, PASS/FAIL 출력 형식)을 그대로 따라 이어붙인다. 각 케이스에는 **왜 이 케이스인지** 한 줄 주석을 단다.
   - 경계값: 입력 크기 최소/최대, 값 범위의 양 끝
   - 함정: 동시 요청/동률, 중복 값, 이미 정렬된 입력과 역순 입력
   - 성능: 제약조건 상한 크기의 입력을 생성해서 **실행 시간을 측정**해 출력

   **기대값 규칙 (중요)**: 기대값은 손으로 검증 가능한 것만 적는다.
   - 직접 계산해서 확신할 수 있으면 기대값을 쓰고, 주석에 계산 근거를 남긴다.
   - 확신할 수 없으면 **기대값을 지어내지 말고** 결과만 출력하거나 성능 측정 전용으로 만든다.
     틀린 기대값은 없는 버그를 쫓게 만들어서 안 만드느니만 못하다.

   성능 케이스 예시(kotlin):
   ```kotlin
   // 성능: 제약조건 상한(jobs 500개) — 기대값 대신 실행 시간만 확인
   val big = Array(500) { intArrayOf(it % 1000, (it % 1000) + 1) }
   val start = System.currentTimeMillis()
   val result = Solution().solution(big)
   println("perf: result=$result elapsed=${System.currentTimeMillis() - start}ms")
   ```

5. **실행해서 확인**: 추가한 케이스를 실제로 돌려본다.
   ```bash
   cd kotlin && ./gradlew runMain -PmainClass=pg.level{N}.p{id}_{slug}.SolutionTestKt
   ```
   (`runMain` 태스크가 없으면 실행은 사용자에게 맡기고, IntelliJ에서 `main` 옆 ▶로 돌리라고 안내한다.)

6. **보고**: 어떤 케이스를 왜 추가했는지, 그중 실패한 케이스가 있으면 그게 현재 풀이의 어떤 약점을 가리키는지 설명한다.
   **고치는 건 사용자 몫이다 — 승인 없이 `Solution` 코드를 수정하지 않는다.**

## 하지 않는 것

- `Solution` 풀이 코드를 대신 고치지 않는다 (원인 설명까지만).
- 검증 못 한 기대값을 지어내지 않는다.
- 정답 풀이를 별도로 작성해서 그걸로 기대값을 만들어내지 않는다 (그건 문제를 대신 푸는 것과 같다). 사용자가 명시적으로 요청하면 그때 한다.
